# Updater game target and loaded SDK checks — 2026-10-04

## Symptoms and evidence

Matt updated through the in-app updater and checked the Updates panel, but AFK remained sequential. The screenshot showed a green matching SDK at `C:/Program Files/Epic Games/Venus/sdk_mods` while the selected folder was Steam. Read-only inspection found desktop 2.28.0, Steam SDK 2.26.0 without concurrent support, and bundled SDK 2.28.0 with concurrent support. `C:/Users/mwenn/AppData/Local/Programs/MSBT/game-setup.log` recorded a successful install into Epic at 2026-10-04T21:17:02Z. The running game executable was the Steam copy.

Root cause: both `detectInstalledSdkmodInfo` and automatic install detection iterated store candidates and accepted the first valid installation. `localVersionInfo` did not receive the selected folder. The updater passed only its parent process ID to Setup; Setup therefore invoked game integration without an explicit target. The desktop version comparison did not establish that the selected game's installed or loaded SDK matched the bundle. This was not failure to download the public desktop release.

## Changes

- `electron_poc/sdk_target.js`: one selection policy, explicit selected path first, then a uniquely identified running installation, then remembered selection, then a single valid discovered installation. Ambiguous discovery asks for a folder; an unavailable explicit/remembered target fails rather than substituting another store. Running/selected installation conflicts are reported.
- `main.js`: version checks and SDK actions use that selection; read-only process inspection identifies the running executable. Target selection is carried into the update handoff, and in-app installation is deferred while the game is open. Installer success requires the SDK hash, mod enablement and PAK install verification. SDK/runtime/resource preservation behavior is retained.
- `preload.js`, `renderer.js`: checks and update handoff include the selected field; changing it invalidates the old green status immediately and rechecks. Stale refresh responses cannot overwrite a subsequently selected folder. The SDK version label explicitly identifies the bundled version. Desktop-current status does not imply game-current status. The card reports installed-file comparison separately from loaded-game verification.
- `persistent_updater.js`, `installer/Program.cs`: carry the exact game root as a structured `--game-root` argument through the external installer process and into the installed application's game setup helper. Paths with spaces remain one argument. Standalone installer folder selection remains available.
- `runtime_identity.py`, `external_bridge.py`: future SDK builds capture archive path/hash/version once at module import and return it in status. Replacing a file on disk does not change that loaded fingerprint. Old SDKs lacking this field remain explicitly unverified while running; disk equality alone is not loaded-runtime proof.

## Validation and rejected approaches

Target-policy and updater-handoff tests pass, including Steam selected while Epic is first, a stale remembered Epic path while Steam runs, ambiguous installations, invalid explicit targets, paths with spaces, and changed/unknown loaded hashes. `test_sdk_checker_integration.js` uses actual Electron main IPC and renderer with temporary Steam/Epic folders: old Steam bytes cannot inherit Epic's matching status; replacing Steam bytes updates only disk status; no running-build claim is inferred.

The installer built/published locally without warnings; all 31 offline installer checks passed. Oak2 helper tests and real offline bundled install tests passed (preserve existing stable/beta/nightly SDKs, protect partial installs, PAK backup/hash verification). Six runtime-identity/startup/import checks passed; an earlier ten-check bridge/startup/import set also passed. Python compilation and JS syntax checks passed. These counts overlap. An initial no-restore installer build failed because its shared assets file lacked the win-x64 target; normal restore/build resolved it without a product code change.

Rejected: treating newest desktop metadata as installed SDK version; trusting the first store found; overwriting every discovered game; claiming a loaded SDK is current from its present disk hash; restarting/killing the game to force completion.
